Comment implémenter
🎯 Objectif de la phase IMPLÉMENTER
La phase IMPLÉMENTER est le cœur du FORGE où les stories déjà prêtes, découpées et
validées en PLANIFIER sont codées, intégrées, testées et documentées. La spécification devient du code fonctionnel, conforme et prouvé.
Implémenter, ce n'est pas juste coder. C'est traduire fidèlement les
spécifications en code, en tests et en preuves de conformité — sans
interpréter, sans deviner, sans improviser.
Principe fondamental : les spécifications atomiques issues de DÉFINIR sont la seule source de vérité. Le développeur code ce qui est spécifié. Le QA teste ce qui est spécifié. L'intégrateur valide ce qui est spécifié. Tout le monde travaille à partir du même artefact.
Note terminologique. Cette page décrit la phase IMPLÉMENTER dans son contexte opérationnel. Pour les définitions de référence des termes utilisés ici — spécification IF… THEN…, spécification atomique, DoR, DoD, validation, vérification, test, niveaux dʼintégration, interfaces, angles dʼobservation, intégration, contrat dʼintégration, CI/CD, artefact, dette technique, qualimétrie, rôles et RACI — voir le Lexique / Terminologies et la page SPÉCIFICATION.
Les descriptions locales précisent lʼusage de ces notions pendant IMPLÉMENTER. Les
contributions indiquées dans cette page sont propres à cette phase et ne remplacent pas la matrice RACI. Les anciens termes comme critère dʼacceptation, cas de test ou scénario convergent ici vers la spécification IF… THEN… et ne doivent pas recréer une couche séparée.

1. 💻 CODER — Traduire la spécification en code
Le code est une traduction directe de la spécification atomique, pas une interprétation.
Le développeur implémente exactement ce qui est spécifié : ni plus, ni moins.
Si la spécification est ambiguë ou incomplète, on ne devine pas : on retourne à DÉFINIR.
Le code respecte les standards de développement, de sécurité et de conformité du Contrat qualité.
Les revues de code sont effectuées et approuvées par les pairs.
2. 🧪 TESTER — Prouver la conformité à tous les niveaux
Les validations et tests sont dérivés directement des spécifications IF… THEN…, sans couche séparée de critères dʼacceptation.
Les tests suivent lʼapproche RED4GREEN : écrire ou ajuster le test qui échoue dʼabord, puis
implémenter jusquʼà obtenir un résultat vert.
Les tests couvrent les niveaux pertinents : Small, Medium et Large / E2E.
Les approches whitebox, blackbox et graybox peuvent s'appliquer à tous les niveaux.
La couverture unitaire minimale est de 60 % lorsque mesurable.
Les spécifications critiques doivent avoir au moins une validation associée et un résultat
documenté.
L'automatisation est la règle ; le manuel est l'exception justifiée. Les tests automatisables doivent être intégrés au pipeline lorsque pertinent.

3. 🔗 INTÉGRER — Assembler et valider les contrats
Le code est intégré dans la branche principale ou la branche de release appropriée.
Les vérifications CI/CD passent sans erreur.
Les contrats d'intégration sont respectés et validés avec les systèmes partenaires.
Les dépendances inter-équipes sont intégrées et testées.
Les artefacts de build sont générés, versionnés et stockés dans les dépôts officiels.
4. 📝 DOCUMENTER — Maintenir la traçabilité vivante
La documentation technique est mise à jour : code, API, configuration, changelog.
La documentation est liée aux spécifications, pas gérée comme un document séparé en silo.
La traçabilité spécification → code → tests → résultats est maintenue.
Les risques, anomalies critiques et dettes découverts pendant l'implémentation sont
documentés et remontés au backlog ÉLICITER pour préserver la boucle de rétroaction.
🔄 La boucle spécification → code → test
Le code et les tests sont deux faces de la même spécification :
1 SPÉCIFICATION ATOMIQUE 2↙              ↘
3 CODE              TESTS 4↘              ↙
5CONCORDANCE 100%
Le code implémente le comportement décrit dans la spécification.
Les tests vérifient que le code respecte la spécification.
Si le test échoue, soit le code est incorrect, soit la spécification doit être clarifiée.
Il n'y a jamais de code sans test, ni de test sans spécification.
Si tu ne sais pas quoi tester, c'est que la spécification n'est pas assez claire. Si
tu ne sais pas quoi coder, c'est pareil.

🤝 Pair testing pendant IMPLÉMENTER
Le pair testing sert à traiter les zones grises dʼintégration avant la diffusion, lorsque le
comportement réel dépend de plusieurs composants, environnements ou responsabilités.
Planifier des sessions ciblées DEV × QA, DEV × IVV, QA × IVV ou dev/ops selon les risques de la story.
Utiliser le pair testing pour valider les contrats dʼintégration, les cas limites, les transitions dʼétat, les prérequis dʼenvironnement et les comportements difficiles à automatiser immédiatement.
Documenter les constats, décisions, anomalies et apprentissages dans Jira ou dans la preuve de validation associée.
Remonter à DÉFINIR les ambiguïtés de spécification et à ÉLICITER les nouveaux besoins, risques ou signaux qualimétrie.

✅ Critères de sortie de IMPLÉMENTER
La phase IMPLÉMENTER est terminée quand :
Toutes les stories planifiées sont implémentées conformément à leurs spécifications IF… THEN….
Le code source respecte les standards de développement, de sécurité et de conformité du Contrat qualité.
Tests unitaires (auto) RED4GREEN réalisés et verts, avec seuil de couverture minimal atteint
lorsque mesurable.
Tests d'intégration (auto) RED4GREEN réalisés et verts lorsque pertinent.
Spécifications fonctionnelles (auto) RED4GREEN validées : les spécifications IF… THEN… sont satisfaites pour chaque story.
Les anomalies critiques ou bloquantes sont corrigées ou remontées au backlog ÉLICITER
avec un plan de résolution.
Les dépendances techniques et inter-équipes sont intégrées et validées.
Les contrats d'intégration sont respectés et les interfaces validées.
Le pair testing requis est réalisé sur les zones grises dʼintégration et les constats sont documentés.
Le code est intégré dans la branche principale et passe les vérifications CI/CD sans erreur.
Les artefacts de build sont générés, versionnés et stockés dans les dépôts officiels.
La documentation technique est mise à jour et liée aux spécifications.
Les revues de code sont effectuées et approuvées.
Les risques et dettes identifiés sont documentés et remontés au backlog ÉLICITER.
Le DoD est satisfait pour chaque story, dépendance et epic concerné.
Les environnements de test et de validation sont stables et prêts pour la phase DIFFUSER.
🔄 Lien avec les autres phases
1 DÉFINIR → spécifications atomiques → PLANIFIER → stories prêtes (DoR) → IMPLÉMENTER → code validé (DoD) → DIFFUSER
2    ↑                                                                          | 3    └──── signaux, cas manquants, incohérences, dette technique ───────────────┘
IMPLÉMENTER est la traduction fidèle des spécifications en code prouvé. Quand cette phase est bien faite, DIFFUSER reçoit un build solide, testé et documenté. Quand elle est bâclée, la dette se paie en bugs, en retravail et en incidents post-livraison.
On ne peut pas bien diffuser ce qu'on n'a pas bien implémenté. Et on ne peut
pas bien implémenter ce qu'on n'a pas bien défini.
