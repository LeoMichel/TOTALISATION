Les métriques de la qualimétrie
Note terminologique : cette page est la référence de travail pour la définition, le choix, lʼimplantation et le bilan des KPI de qualité, peu importe lʼoutil utilisé pour les mesurer ou les présenter : Grafana, Power BI, Excel, Jira, Xray, SonarQube, Prometheus ou autre. Pour les définitions de référence des termes utilisés ici — métrique, KPI, qualimétrie, seuil, tendance, couverture, validation, observabilité, log, trace, incident, dette technique, SLA/SLO, MTTR, DORA, CI/CD, backlog et rôles — voir le Lexique / Terminologies.
La page Qualimétrie officielle OPAL-RT sert davantage à présenter la qualimétrie, son
intention, sa portée organisationnelle et sa lecture globale. La présente page sert plutôt à documenter concrètement quelles métriques existent, pourquoi elles ont été choisies, comment elles sont calculées, où elles sont implémentées et si elles sont utilisables.
Cette page remplace lʼidée dʼun guide uniquement « Grafana » par un référentiel opérationnel des KPI de qualité. Grafana peut demeurer le board principal lorsque disponible, mais les KPI peuvent aussi provenir de Power BI, Excel, Jira, Xray, SonarQube, exports manuels contrôlés ou tout autre outil pertinent. Lʼimportant est de garder une définition commune, une source claire, un propriétaire, un statut dʼimplantation et une lecture utile pour les décisions qualité.
Positionnement de cette page
Le référentiel doit rester aligné sur les codes de métriques de la qualimétrie : STAB, QUAL, DEL,
SUP, UX, XRAY, VAL, FLOW, FB, CONF, CODE, SEC, ENV, DEP et ARCH. Si une métrique nʼest pas encore claire, elle doit être élicitée, définie et priorisée avant dʼêtre ajoutée comme KPI officiel. Cette page documente donc le cycle complet : besoin de mesure → définition → source → outil → statut → bilan dʼutilisation.
Architecture cible multi-outils
Vision simple recommandée, indépendante de lʼoutil de visualisation :
1 [Sources OPAL-RT] 2↓
3 [Collecte automatisée ou contrôlée : API, exports, exporters, webhooks, fichiers maîtrisés] 4↓
5 [Stockage / préparation : Prometheus, PostgreSQL, data mart, Excel contrôlé au besoin] 6↓
7 [Visualisation : Grafana, Power BI, Excel, Jira dashboards, rapports Confluence] 8↓
9 [Revues SDLC, contrats qualité, décisions Go / No-Go, amélioration continue]
Conseil clé : privilégier lʼautomatisation via Prometheus, SonarQube API, Jira API, Xray API, pipelines CI/CD ou connecteurs Power BI lorsque possible. Utiliser Excel, PostgreSQL ou une source contrôlée seulement pour les données qui ne sont pas encore automatisables, avec un propriétaire clair, une fréquence de mise à jour et une cible dʼautomatisation.
Positionnement : cette page est le référentiel opérationnel des KPI de qualité. Elle centralise les définitions, formules, sources, seuils, propriétaires, statuts dʼimplantation et bilans dʼusage. Elle alimente notamment la Cérémonie de la qualimétrie, où les indicateurs sont revus, interprétés et transformés en actions, décisions ou signaux à retourner vers les phases appropriées du SDLC.
Contenu KPI à centraliser dans cette page

Registre détaillé des KPI de qualité
Cette section est le registre principal des métriques et informations KPI de qualité. Lʼobjectif est
de conserver ici la définition opérationnelle des indicateurs, peu importe lʼoutil utilisé pour les afficher ou les exploiter.
Question directrice : avant dʼajouter ou de promouvoir une métrique comme KPI officiel, se demander : « quʼest-ce qui fait que lʼon pense que cela représente un risque pour la qualité ? » La réponse aide à choisir la bonne mesure, le bon seuil, la bonne source et la bonne action attendue.

Scorecard globale alignée sur Qualimétrie
Formule pondérée recommandée :
1 Score global =
2 15% Delivery (DEL / DORA)
3 + 20% Qualité code (CODE / SonarQube) 4 + 15% Santé produit (STAB)
5 + 15% Sécurité (SEC)
6 + 10% Maturité équipe et flow (FLOW)
7 + 10% Environnements et infrastructure (ENV) 8 +  5% Dépendances et 3rd party (DEP)
9 + 10% Conformité aux standards (CONF)
Ramener chaque KPI sur une échelle 0–100.
Afficher la valeur actuelle, la tendance 7 jours et la tendance 30 jours.
Utiliser les seuils de la page Qualimétrie lorsquʼils existent.
Déclencher une discussion lorsque le score se dégrade, plutôt que traiter le score comme une vérité absolue.
Repères visuels recommandés : 🔴 <50 critique | 🟡 50–75 moyen | 🟢 >75 sain.
Astuce Grafana : utiliser les Transformations, Field calculations et variables de dashboard pour agréger les scores. Pour les calculs plus complexes ou historiques, préférer une table PostgreSQL préparée par un ETL léger.
Exemples de requêtes de départ
Prometheus — STAB-02 Error rate
1 sum(rate(http_requests_total{status=~"5.."}[5m])) 2 /
3 sum(rate(http_requests_total[5m]))
Prometheus — STAB-05 Latency p95
1 histogram_quantile( 2 0.95,
3 sum(rate(http_request_duration_seconds_bucket[5m])) by (le, service) 4 )
SQL — DEL-02 Lead time
1 SELECT
2 avg(deployed_at - created_at) AS lead_time 3 FROM jira_work_items
4 WHERE deployed_at IS NOT NULL
5 AND issue_type IN ('Story', 'Bug', 'Feature');
SQL — DEL-03 Cycle time
1 SELECT
2 avg(done_at - in_progress_at) AS cycle_time 3 FROM jira_work_items
4 WHERE done_at IS NOT NULL
5 AND in_progress_at IS NOT NULL;
SQL — CONF-02 Taux de Go/No-Go documenté
1 SELECT
2 100.0 * count(*) FILTER (WHERE go_no_go_documented = true) / count(*) AS go_no_go_documentation_rate
3 FROM releases
4 WHERE release_date >= current_date - interval '90 days';
SonarQube API — CODE-04 Coverage tests
1 /api/measures/component? component=PROJECT_KEY&metricKeys=coverage,line_coverage,branch_coverage
SonarQube API — CODE-02 / CODE-03 / CODE-05
1 /api/measures/component? component=PROJECT_KEY&metricKeys=duplicated_lines_density,code_smells,sqale_index,sqale_debt_ ratio
Intégration des sources
SonarQube : utiliser lʼAPI REST ou un plugin Grafana compatible pour alimenter les métriques CODE et une partie de SEC.
Jira : utiliser lʼAPI REST, un export planifié ou une base intermédiaire pour les métriques DEL,
SUP, FLOW, ARCH et CONF.
Xray : connecter les données dʼexécution, de couverture et de traçabilité pour XRAY, QUAL et
CONF.
CI/CD : connecter les pipelines disponibles pour les taux de succès, déploiements, rollback, tests automatisés et preuves DoD.
Prometheus : privilégier Prometheus pour les métriques de disponibilité, latence, erreurs, infrastructure et services instrumentés.
Docker / Kubernetes : exposer les métriques dʼenvironnements, déploiements et ressources
lorsque les produits ou environnements concernés les utilisent.
Logs et traces : utiliser Loki, OpenTelemetry ou la solution disponible pour relier erreurs,
incidents, latence et usage réel.
Données manuelles contrôlées : tolérées au départ pour les métriques non automatisées, mais chaque donnée manuelle devrait avoir un propriétaire, une fréquence de mise à jour et une cible dʼautomatisation.
Règles de nommage recommandées
Nommer les panneaux avec le code de métrique en premier : DEL-02 — Lead time, CODE-
04 — Coverage tests, CONF-05 — Traçabilité spécifications → validations → résultats.
Afficher la source dans la description du panneau : Jira, Xray, SonarQube, Prometheus,
CI/CD, Support, etc.
Afficher la formule ou le lien vers la requête lorsque possible.
Indiquer les seuils utilisés et préciser sʼils proviennent de la page Qualimétrie ou dʼun
ajustement propre au produit.
Éviter les panneaux anonymes comme « qualité », « performance » ou « santé » sans code de
référence.
Bonnes pratiques critiques
1. Commencer petit : prioriser quelques métriques utiles plutôt quʼun dashboard complet mais
non maintenu.
2. Relier chaque panneau à une décision : si personne ne sait quoi faire avec un KPI, il nʼest
pas encore utile.
3. Normaliser les scores : ramener les KPI synthétiques sur une échelle 0–100, tout en conservant la métrique brute accessible.
4. Privilégier les tendances : afficher 7 jours et 30 jours plutôt quʼun simple snapshot.
5. Définir des seuils visibles : rouge = critique, jaune = à surveiller, vert = sain, selon les seuils
de Qualimétrie.
6. Assigner un ownership : chaque KPI doit avoir un propriétaire de donnée et un circuit dʼaction, conformément à la matrice RACI.
7. Documenter les exceptions : une métrique absente, manuelle ou incomplète doit être visible plutôt que masquée.
8. Réviser régulièrement : un dashboard de qualimétrie doit évoluer avec les risques qualité, les produits et la maturité de collecte.
